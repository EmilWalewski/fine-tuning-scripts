# Stateless Chunk Regeneration

## Why this exists

Datasets of document chunks (`instruction` / `input` / `output`, one record per
chunk) are often generated by a **single stateful agent conversation** that
walks through a folder with handoffs carrying figures forward. The result looks
fine but is quietly contaminated: an `output` ends up containing a number,
name, or date that belongs to a *different* chunk's `input`. For fine-tuning
this is poison — the model learns to invent facts that aren't in the prompt.

The cure is **statelessness**: process every chunk in its own fresh context that
can see *only that one chunk* and physically cannot reach the others. This skill
codifies that as a resumable, non-destructive pipeline driven by isolated
subagents — one subagent per chunk.

The four guarantees this workflow upholds, and why each matters:

1. **Isolation** — each subagent reads exactly one input file and is forbidden
   from listing/reading anything else. No neighbour's figures are reachable, so
   bleed is impossible by construction, not by good behaviour.
2. **Non-destructive** — outputs go to a fresh `_outputs_v2/`; the original data
   is never touched until you explicitly merge. You can always compare or roll
   back.
3. **Idempotent / resumable** — "what's left" is computed from the filesystem
   (missing or empty output files), so session limits, crashes, or partial
   batches cost nothing. Just re-run and continue.
4. **Verifiable** — a numeric leak detector proves whether contamination is
   actually gone, rather than trusting that it is.

## The pipeline

```
build_manifest.py  →  [drive subagent batches]  →  leak_qa.py + validate_outputs.py  →  merge_to_jsonl.py
   (stage 1)            (stage 2, the core)             (stage 3 QA)                  (stage 4)
```

Scripts live in `scripts/`. Run them with the user's normal `python3`. They are
stdlib-only. The one stage that is NOT a script is stage 2 — spawning subagents
requires the Agent tool, so you drive it yourself, in batches.

---

### Stage 1 — Build the manifest and per-chunk inputs

```bash
python3 scripts/build_manifest.py --src <FOLDER_OF_JSONL> [--work /tmp/chunk-regen] [--out <SRC>/_outputs_v2] [--window 8100]
```

This writes `<work>/manifest.json`, one `<work>/inputs/<key>.txt` per record,
and `<work>/RULES.md` (the analyst contract + isolation + output rules). Confirm
the record count matches what the user expects before going further.

**Context window / length budget (`--window`, default 8100).** Fine-tuning packs
`instruction + input + output` into one fixed window (8192 for Llama 3). The
input is fixed, so the only safe lever is output length — truncating a generated
summary after the fact destroys exactly the signal you're training on. With a
window set (it is, by default), the manifest gets a per-record `out_char_budget`
= window − input_tokens − reserve, and stage 2 passes that cap to each subagent
so outputs fit **by construction**. Override the default when the user names a
window in their prompt (e.g. "keep everything under 4096 tokens" → `--window 4096`);
pass `--window 0` to disable budgeting entirely. Install `tiktoken` for accurate
counts (cl100k_base, a conservative proxy); without it a chars/token heuristic is
used. A warning prints if any input nearly fills the window (tiny output budget).

**The RULES file is the contract every subagent obeys.** The default
(`assets/RULES_TEMPLATE.md`) is a dense corporate-report analyst prompt. If the
user's task is different (different domain, different output style), open
`<work>/RULES.md` and rewrite the analyst portion at the top — but **leave the
`ABSOLUTE ISOLATION CONSTRAINT` and `OUTPUT INSTRUCTION` sections intact**, since
those are what make isolation and clean file output work. You can also pass a
fully custom template with `--rules`.

### Stage 2 — Drive isolated subagent batches (the core)

Repeat this loop until nothing remains:

1. Ask the driver script what's left (it also dumps the list to JSON):
   ```bash
   python3 scripts/remaining.py --manifest <work>/manifest.json --limit 15
   ```
2. For each line it prints, spawn **one** `general-purpose` subagent. Send the
   whole batch (≈10–15) **in a single message** so they run concurrently. Use
   this exact prompt — short, so the subagent spends its budget on the chunk,
   not on parsing instructions:

   ```
   Read your full instructions from <work>/RULES.md and follow them exactly.
   Your single input file: <input_path>
   Write your summary to: <output_path>
   Do not read or list any other file. Reply only OK when done.
   ```
   When `remaining.py` appends `|| BUDGET=<N>` (window mode is on), add one line
   so the output fits the context window:
   ```
   Hard limit: your summary must not exceed <N> characters.
   ```
3. Re-run `remaining.py` and go again with the next batch.

Why batches of ~15 driven by the filesystem, rather than one giant fan-out:
the `remaining.py` recompute makes every round self-correcting. If a subagent
silently failed, its output file won't exist, so the next round simply picks it
up again — you never need to track which agent did what.

**Notes that save real pain:**
- A subagent that returns a usage block with `total_tokens: 0` and a "session
  limit" message often **still wrote its file** before the limit hit on its
  final reply (it used its tools first). Don't assume failure — let
  `remaining.py` be the source of truth. If the limit is real, wait and resume;
  the loop is idempotent.
- `INSUFFICIENT_DATA` is a **valid** output (a chunk with no factual content),
  not a failure. It produces a tiny file; that's expected. Don't retry it.
- Keep batch size modest. Concurrency is capped anyway, and smaller batches give
  the user tighter progress feedback.

Periodically sanity-check progress:
```bash
D="<out_dir>"; echo "files=$(ls "$D"|wc -l) empty=$(find "$D" -type f -empty|wc -l)"
```
`empty` should always be 0.

### Stage 3 — Leak QA (prove contamination is gone)

```bash
python3 scripts/leak_qa.py --manifest <work>/manifest.json [--verbose]
python3 scripts/validate_outputs.py --manifest <work>/manifest.json [--verbose]
```

It flags any output containing a distinctive number (≥6 digits, dates excluded)
that is **absent from its own input but present in another chunk's input** —
the fingerprint of bleed. The target is `CLEAN`. If records are flagged, re-run
just those chunks through stage 2 (delete their output files first so
`remaining.py` re-queues them) and re-check.

The date filter intentionally strips both numeric dates and English
"Month D, YYYY" forms, because shared dates are the main source of false
positives. A flagged number is strong evidence but not proof — eyeball flagged
records with `--verbose` before acting.

`validate_outputs.py` catches training-poison that leak detection cannot see:
prompt-marker leakage (`### Instruction/Input/Output`), outputs over the stored
character budget, likely truncated endings, suspicious million-unit formatting
(`PLN 964,251M`), and common `tys. zł` conversion mistakes such as
`56 887 tys. zł -> 568.9M PLN` instead of `56.9M PLN`. Any flagged record should
be regenerated before merge: delete only its output file, re-run `remaining.py`,
then repeat both QA commands.

---

### Stage 4 — Merge back into a dataset (non-destructive)

```bash
python3 scripts/merge_to_jsonl.py --manifest <work>/manifest.json --src <FOLDER_OF_JSONL> --out <NEW>.jsonl
```

This preserves each record's original `instruction` and `input` and swaps in the
regenerated `output`, writing a brand-new JSONL. The source folder is untouched.
Only point the training script at the new file after the user has seen the QA
result. Missing/empty outputs are skipped with a warning by default
(`--keep-missing` to emit them empty instead).

## Quick reference

| Stage | Command | Produces |
|---|---|---|
| 1 | `build_manifest.py --src F [--window 8100]` | manifest.json, inputs/, RULES.md |
| 2 | `remaining.py --manifest M --limit 15` + spawn subagents | output `.txt` per chunk |
| 3a | `leak_qa.py --manifest M` | CLEAN / flagged list (contamination) |
| 3b | `validate_outputs.py --manifest M` | prompt leaks, bad units, truncation, budget issues |
| 3c | `measure_tokens.py --manifest M --src F --window 8192` | which records overflow the window |
| 4 | `merge_to_jsonl.py --manifest M --src F --out NEW.jsonl` | merged dataset |

**Length verification & re-fit.** After generation, run `measure_tokens.py` with
the real training window. Any record it lists as over-window gets re-fit: delete
its output file (so `remaining.py` re-queues it), tighten its `out_char_budget`
in the manifest (or just pass a smaller `Hard limit` in the subagent prompt), and
re-run that one through stage 2. Repeat until `measure_tokens.py` reports all
records fit. This is the loop that lets you keep a generous window (e.g. 8192)
with zero truncated summaries.

## Resuming with a different agent or a fresh session

This pipeline has **no in-memory state** — everything lives on disk (the work
dir and the output dir). That means any agent can take over from where another
left off: a new subagent, a brand-new conversation, even a different machine
pointed at the same paths. There is no handoff document to write and no "where
was I" to reconstruct.

To continue someone else's (or your own earlier) run, you need only three paths,
all of which already exist on disk:

- `<work>/manifest.json` — the full record list
- `<work>/inputs/` — the per-chunk inputs
- the output dir (e.g. `<src>/_outputs_v2`) — where finished summaries accumulate

Then just resume the stage-2 loop:

```bash
python3 scripts/remaining.py --manifest <work>/manifest.json --limit 15
```

It recomputes what's left from the filesystem, so already-finished chunks are
never redone and partially-completed batches simply continue. Completion is
tracked per chunk (one output file each), not per batch — so a run that died in
the middle of a batch loses nothing but the chunks that hadn't been written yet.

One caveat to be honest about: the "done" test is *file exists and is non-empty*.
If an agent were killed in the exact instant of writing a file (very unlikely —
`Write` emits the whole file at once), you could get a truncated output that the
check treats as done. The stage-3 `leak_qa.py` pass plus a final size sanity
check (`find <out> -type f -printf '%s %p\n' | sort -n | head`) is your safety
net for spotting any such anomaly.

## Cleanup

The work dir (`/tmp/chunk-regen` by default) holds only derived artifacts —
manifest, per-chunk inputs, RULES. Safe to delete once the merge is verified.
Confirm with the user before removing anything outside the work dir.
